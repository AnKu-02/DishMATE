## 1. The big picture

"Sim-to-real" means: build and test something in simulation, then make it work on the real system.
There were **two separate gaps** to close, and they behaved very differently.

| | Motion (where the arm goes) | Perception (is the plate dirty?) |
|---|---|---|
| Simulation | RoboDK station with the MAiRA, racks, table, plates | Plate images rendered by a RoboDK camera |
| What transferred | Almost everything: poses agree within 6.45 mm / 0.19° | Almost nothing: 25.4% correct on the robot camera |
| How we closed the gap | Use the robot's own taught points and kinematics in the twin | Fine-tune on 63 real robot-camera images → 96.8% |

The key design decision for motion: **the robot is the source of truth, RoboDK is the copy.**
Points are taught on the real robot, exported from the controller, and loaded into RoboDK in the
robot's own coordinate frame. RoboDK is then used to *check* the sequence (reach, collisions, the
long base rotation) before the real arm runs it, and later to *mirror* the real arm live.

```
            teach on pendant                      export (read-only)
 real MAiRA ────────────────► point database ─────────────────────────► gp_points.json
     ▲                                                                       │
     │  pick_cycles.py / UI (joint moves to the same named points)           │ build_station.py
     │                                                                       ▼
     └──────────── /joint_states ───► UI backend /api/twin ───► twin.py ──► RoboDK station
                         (live mirror, read-only, RoboDK stays in simulation mode)
```

> An earlier approach went the other way: targets were made in RoboDK and a RoboDK post-processor
> generated NEURA Python code (see `Dishwasher_Rack_Code.py`, header "Program generated by RoboDK
> v6.0.3 … Using nominal kinematics"). That works, but the code depends on RoboDK's *nominal*
> robot model and on the RoboDK cell matching the real cell exactly. Teaching on the robot and
> exporting into RoboDK removes both risks, so the final workflow uses that direction.

## 3. Concepts you need first

### 3.1 Joint targets vs. Cartesian targets

A **Cartesian target** is a position and orientation of the tool (x, y, z, rotations). A 7-axis arm
can reach the same Cartesian pose with many different joint configurations, so the simulator may
choose a different arm shape than the real robot.

A **joint target** is the 7 joint angles themselves. It is unambiguous: the arm shape is fixed.
**This project uses joint targets everywhere** (`target.setAsJointTarget()` in RoboDK,
`move_joint` on the robot), which is the main reason the sim and the robot behave the same.

### 3.2 Frames: base, flange, TCP

```
 robot base frame ──(joint angles, forward kinematics)──► flange ──(tool offset)──► TCP
                                                          (end of arm)              (between the RG6 fingers)
```

- **Base frame**: the robot's own origin. Everything in this project is expressed in it.
- **Flange**: the mounting plate at the end of the arm. Its pose follows from the joint angles
  (forward kinematics, "FK").
- **TCP** (tool centre point): the point that matters for grasping. For the RG6 here it is
  180 mm in front of the flange (compare `flange_m_rad` and `tcp_m_rad` z values in
  `robodk_sim/gp_points.json`: 1.0236 m vs 0.8436 m).

If RoboDK and the controller disagree on **the base frame**, **the kinematics**, or **the tool
offset**, the twin will be wrong. The export/build steps below make all three come from the
controller.

### 3.3 NEURA pose format

NEURA poses are `[x, y, z, a, b, c]` in **metres and radians**, rotation order
`Rz(c)·Ry(b)·Rx(a)`. RoboDK works in **millimetres and degrees**. `build_station.py` converts with:

```python
def neura_pose(values):
    x, y, z, a, b, c = values
    return xyzrpw_2_pose([x * 1000, y * 1000, z * 1000, math.degrees(a), math.degrees(b), math.degrees(c)])
```

### 3.4 Joint 1 is limited to ±180°

The dishwashing rack is behind the robot, beyond the joint-1 limit, so the dirty route turns about
**295°** around the base while holding a plate. `robot_motion.plan_target` chooses, for every move,
the joint-1 angle equivalent (±360°) that is inside ±180° and closest to the current angle, and
refuses any move that would turn a joint more than a full circle. This is exactly the kind of
motion you want to see in simulation (with collision checking) before the real arm does it.

### 3.5 The RG6 command polarity

On this RG6 setup `robot.gripper("on")` **opens** and `robot.gripper("off")` **closes**
(observed 2026-10-09). `robot_motion.MairaArm.open_gripper()` / `close_gripper()` hide this, so
always use those helpers.

## 4. Motion: from taught points to a verified twin

### Step 1 — Teach the points on the pendant

Teach each point at the real position, with the RG6 tool active, and store it in the robot's
point database under these names (they are the defaults in `settings.json`):

| Point | Role |
|---|---|
| GP156 | Observe pose: camera looks at the mixed plates rack |
| GP157, GP163 | Pick poses, one per plate |
| GP161 | Lift: raise the plate clear of the rack before moving away |
| GP165 | Via point before and after the clean drop |
| GP164 | Clean drop above the stacking table |
| GP166, GP167 | Two slots in the dishwashing rack (dirty drops) |

Why taught and not computed: the taught point already contains the real rack position, real
plate height and real calibration. Nothing has to be measured by hand.

### Step 2 — Export the points from the robot (read-only)

In WSL, with the ROS environment active and the robot reachable:

```bash
source ./activate_wsl.sh
python robodk_sim/export_gp_points.py
```

It never moves the robot. For every point it saves to `robodk_sim/gp_points.json`:

- `joints_rad` / `joints_deg` — from the point database (`db.get_joint_positions(name)`)
- `flange_m_rad` — the controller's FK for those joints, **without** tool
  (`robot.compute_forward_kinematics(joints, target_frame="flange")`)
- `tcp_m_rad` — the TCP pose stored when the point was taught

plus one `live_sample` (current joints, flange pose, TCP pose) that gives the controller's
flange→TCP transform for the active tool, and the `sequence` from `settings.json`.

Example output line:

```
GP156: joints(deg)=[172.8, 59.1, -133.7, -92.9, 6.4, 59.0, -13.0]  tcp(mm)=[...]
```

Re-run this whenever you re-teach a point.

### Step 3 — Build the RoboDK station from the export

Two ways:

```text
A) Inside RoboDK: open the station, then Tools > Run Script (or drag robodk_sim\build_station.py
   into the RoboDK window). Save the station afterwards.

B) From a Windows terminal, with no other RoboDK open:
   C:\RoboDK\Python-Embedded\python.exe robodk_sim\build_station.py IN.rdk OUT.rdk
```

What the script does, in order (read `robodk_sim/build_station.py` alongside this list):

1. **Finds the MAiRA** — the robot item with 7 axes (gripper mechanisms are robot items too).
2. **Checks the kinematics.** For every exported point it computes RoboDK's flange pose
   (`robot.SolveFK(joints_deg)`) and compares it with the controller's flange pose:

   ```
   Frame check (RoboDK FK vs NEURA controller FK): max 6.45 mm, 0.190 deg
   OK: RoboDK's nominal MAiRA model matches the calibrated controller within a few mm.
   ```

   It warns above 10 mm or 1°. This single number tells you whether the twin can be trusted.
3. **Creates the frame** `Dishwashing (NEURA base)` at the robot base, so RoboDK coordinates
   equal NEURA coordinates.
4. **Creates the tool** `RG6 (real TCP)` from the live sample:
   `tool_pose = inv(flange) * tcp`. Same TCP as the controller.
5. **Creates joint targets** GP156 … GP167 with the exported joint angles.
6. **Places the scene from the points**, not by hand:
   - plates hang below the pick TCPs (`PLATE_DIAMETER / 2 - GRIP_DEPTH` along tool Z),
   - the mixed plates rack ("Dish rack") is put around and under the two plates,
   - the stacking table ("Table") is put under the clean drop,
   - the dishwashing rack ("Dishwasher rack") is put under the dirty drops,
   - CLEAN / DIRTY signs are added (hidden) above the rack.
7. **Writes helper scripts** into `robodk_sim/generated/` and adds them to the station:
   `Gripper_Open`, `Gripper_Close` (attach the closest plate to the tool), `Take_Photo`,
   `Reset_Plates`, `Show_Clean`, `Show_Dirty`.
8. **Creates the program** `Dishwashing_Sim` (demo: plate 1 dirty, plate 2 clean):

   ```
   GP156 (open, photo, result) -> pick (close, 2 s) -> GP161 ->
       clean: GP165 -> GP164 (open, 5 s) -> GP165 -> GP156
       dirty: GP166 (open, 5 s) -> GP156
   ```

RoboDK has no RG6 model, so the station's OnRobot 2FG7 is shown in its place; its fingers open
and close with the gripper, but plates are always held at the real RG6 TCP.

Re-running the script deletes and recreates everything it made, so it is safe to repeat.

### Step 4 — Verify in simulation

In RoboDK:

1. Turn **collision checking on** (the collision toggle in the toolbar / Tools menu).
2. Double-click `Reset_Plates`, then double-click `Dishwashing_Sim` to run it.
3. Watch for:
   - red collision highlights, especially during the long base turn to the dishwashing rack,
   - the plate staying attached from pick to drop (it should move with the gripper),
   - the arm shape at every point matching what you saw on the pendant.
4. Double-click any target (e.g. `GP166`) to jump the robot to it and inspect it.

Only when the program runs cleanly in the twin, with the grasped plate, does the same sequence
go to the real robot.

You can also script checks with the RoboDK API from RoboDK's Python, for example:

```python
from robodk.robolink import Robolink, ITEM_TYPE_ROBOT
RDK = Robolink()
robot = RDK.Item("Neura MAiRA M", ITEM_TYPE_ROBOT)
for name in ["GP156", "GP157", "GP161", "GP165", "GP164", "GP166"]:
    robot.setJoints(RDK.Item(name).Joints())
    print(name, "collisions:", RDK.Collisions())   # needs collision checking enabled
```

## 5. Running on the real robot

**Safety first.** Robot in **Automatic** mode, area clear, e-stop in reach, speed 20%. The pendant
e-stop is the only immediate stop; software Stop finishes the current plate.

### Step 5 — Dry run (no motion)

```bash
source ./activate_wsl.sh
python pick_cycles.py --dry-run
```

This connects, loads every point from the database, and prints the joint turns each move would
make, using the same `plan_target` the real run uses. The output has this shape (the numbers
depend on where the arm is when you start):

```
GP156: joint turns (deg) <j1>, <j2>, <j3>, <j4>, <j5>, <j6>, <j7>
GP157: joint turns (deg) ...
```

Look for unexpectedly large turns before you let the arm move.

### Step 6 — Run it

Three ways, from simplest to fullest:

```bash
python pick_cycles.py --gui          # both plates, one drop point, live sorting window (Q = stop after cycle)
python sort_gui.py --robot           # Space runs sorting cycles; needs clean_place / dirty_place set
python -m ui.backend.server          # web UI on http://localhost:8080 — Start / Pause / Stop, real sorting
```

What happens per plate (UI version, `ui/backend/dishwashing.py`):

```
observe GP156 → open gripper → photo → classify
   → pick GP157/GP163 → close (wait 2 s) → lift GP161
   → clean: via GP165 → drop GP164 → open (5 s) → via GP165 → GP156
   → dirty: next free slot GP166/GP167 → open (5 s) → GP156
```

`MairaArm` (`robot_motion.py`) adds three safety checks the simulation does not need:

- it loads **all** points before any motion (a missing name fails early),
- it checks the **gripper/tool is loaded** before any motion (`check_gripper`),
- after each move it checks the robot **actually arrived** within 1°.

## 6. The live digital twin

Once the real robot runs, RoboDK becomes a **mirror**: it shows what the real robot is doing, in
real time. Nothing is ever sent from RoboDK to the robot.

### Start everything with one click

Double-click `run_dishwashing.bat`, or:

```bat
C:\RoboDK\Python-Embedded\python.exe run_dishwashing.py
```

It:

1. starts the UI backend in WSL (`python -m ui.backend.server`),
2. opens RoboDK with `settings.json → robodk_station` if RoboDK is not already open,
3. opens `http://localhost:8080/#/dishwashing`,
4. runs the twin loop until Ctrl+C, then stops the backend.

### How the twin works

```
/joint_states ──► ui/backend/joints.py ──► GET /api/twin ──► robodk_sim/twin.py (20 Hz) ──► RoboDK
```

See the data yourself:

```bash
curl http://localhost:8080/api/twin
```

The answer looks like this (values shortened and illustrative):

```json
{"joints_rad": [3.01, 1.03, -2.33, ...], "joints_age_s": 0.03, "gripper": "closed",
 "run_id": 2, "status": "running", "step": "Lifting (GP161)", "result_id": 5,
 "latest": {"label": "dirty", "score": 0.84, "pick": "GP157", "place": "GP166"}}
```

`twin.py` then:

- sets the RoboDK robot to the real joint angles (skips redraws below 0.02° change),
- on `gripper: closed` attaches the closest plate to the tool; on `open` releases it,
- on a new classification colours that plate (green clean / red dirty) and shows the sign,
- on a new run (`run_id` changes) puts the plates back in the rack.

It refuses to start unless RoboDK is in **simulation mode** (`RUNMODE_SIMULATE`).

Run only the twin (backend already running):

```bat
C:\RoboDK\Python-Embedded\python.exe robodk_sim\twin.py
```

## 7. Perception: from simulated images to the robot camera

### 7.1 The simulation-trained classifier

The original classifier was trained on 400 images: 200 rendered by a RoboDK camera and 200 photos
of plates on a table, split at random 80/20 (320 train, 80 test). It scored 100% on its 80 test
images and sorted both plates correctly in the twin.

The simulated camera loop is in `DirtyvsClean_Plates.py`:

```python
camera = RDK.Item('Camera 1')
RDK.Cam2D_Snapshot(img_path, camera)        # render the RoboDK camera view to a PNG
frame = cv2.imread(img_path)
img = cv2.resize(frame, (224, 224)) / 255.0  # full image, BGR, scaled to [0, 1]
prediction = model.predict(img)              # MobileNetV2 + sigmoid → P(dirty)
```

To add your own simulated camera from Python, attach it to a frame (or the tool) and render it:

```python
cam = RDK.Cam2D_Add(frame, "FOCAL_LENGTH=6 FOV=40 FAR_LENGTH=30000 SIZE=640x480 SNAPSHOT=640x480")
RDK.Cam2D_Snapshot(r"C:	emp\sim_plate.png", cam)
RDK.Cam2D_Close(cam)
```

The camera looks along the frame's +Z axis, with +X to the image right and +Y down.

### 7.2 Measuring the gap on the robot camera

Capture labelled photos at the observe pose and classify them with the original model:

```bash
source ./activate_wsl.sh
python camera_viewer.py --interval 10 --item plate --label dirty --plate-id plate_01   # capture
bash setup/run_classifier_python.sh classify_image.py --cnn captures/2026-10-20/plate_5.png
python main_real.py --image captures/2026-10-20/plate_5.png --expected dirty         # logs to results.csv
```

Result: **16 of 63 correct (25.4%)**, and 36 of 41 dirty plates were called clean. The 100% in
simulation said almost nothing about the robot camera. Reasons:

- the real plate is small, at an angle, in front of a cluttered background (simulated plates
  filled the frame on a plain background),
- the model was fed **BGR scaled to [0, 1]**, but MobileNetV2 was pre-trained on **RGB scaled to
  [−1, 1]** — an input-format bug that hid in simulation,
- the decision layer had learned features of the training images that do not exist on the
  robot camera.

### 7.3 Fine-tuning on robot-camera images

`rack_classifier.py` keeps the ImageNet MobileNetV2 features and changes three things:

1. **Crop** the plate area: `ROI = (0.20, 0.95, 0.0, 0.72)` (x0, x1, y0, y1 as fractions of the
   photo at GP156), so stains cover more pixels.
2. **Correct input format**: BGR → RGB and `preprocess_input` (scales to [−1, 1]).
3. **Retrain only the decision layer** — a logistic regression on the 1280 features, with clean
   and dirty weighted equally (41 dirty vs 22 clean).

The labels are a simple CSV, `datasets/rack_labels.csv` (63 rows):

```csv
image,label,note
captures/2026-10-09/plate_1.png,dirty,
captures/2026-10-09/plate_2.png,dirty,
```

Train (classifier environment):

```bash
/root/.venvs/dishwashing-classifier/bin/python rack_classifier.py train
```

It first tests honestly — each capture **day/session is held out** in turn, the layer is trained
on the other days and tested on the held-out one — then trains on everything and saves
`models/plate_rack_head.npz`:

```
Leave-one-day-out: 97% correct (2 wrong of 63; 41 dirty, 22 clean)
  wrong: captures/.../plate_N.png
Saved models/plate_rack_head.npz
```

Why hold out whole sessions and not random images? Photos from one session are near-duplicates.
A random split puts near-copies of the test image in the training set and inflates the score —
that is exactly why the original 100% was misleading.

Ablation (one change at a time, same 63 images): retrained layer 88.9% → + RGB [−1, 1] 92.1% →
+ crop 96.8%. With only 16 labelled images it already reached 89.7%.

`classify_image.py` uses the rack classifier by default; `--cnn` selects the original model.

### 7.4 End-to-end check

In live runs the fine-tuned model made 14 sorting decisions on new images (8 dirty, 6 clean), all
correct by visual inspection of the saved photos. Every classified photo is saved under
`captures/` and logged in `captures/results.csv`.

## 8. Gaps we found and how each was fixed

| Gap (not modelled in the twin) | Symptom on the robot | Fix |
|---|---|---|
| Joint path between taught poses | Unexpected long joint-1 turns | `plan_target` picks the closest joint-1 equivalent inside ±180°, refuses > 360° turns; `--dry-run` prints turns first |
| Gripper command polarity | "Close" opened the gripper | `open_gripper()` = `gripper("on")`, `close_gripper()` = `gripper("off")` |
| Leaving the grasp without lifting | Plate/gripper contact with the rack | Added the lift pose GP161 after every pick |
| Tool setting of the controller | Gripper not loaded; likely cause of the one stopped cycle | `check_gripper()` loads the pendant's selected tool and fails before any motion if missing |
| Classifier input format | 25.4% on the robot camera | RGB scaled to [−1, 1] |
| Image domain (background, angle, scale) | Dirty plates called clean | Plate crop + retrained decision layer on 63 real images |

Pattern to remember: **the twin is excellent at geometry (reach, collisions, frames) and blind to
everything else** — I/O polarity, controller state, tool configuration, camera images.

## 9. Troubleshooting

| Problem | Check |
|---|---|
| `GP… not found in the robot point database` | Point name typo, or not saved on the pendant |
| Frame check warns > 10 mm | Wrong robot model in the station, or points exported with a different tool |
| Plates float above/below the rack in RoboDK | Tool offset wrong → re-export with the RG6 tool active, rebuild |
| `Gripper not ready …` | On the pendant select and activate the RG6 tool again, then Start |
| `Did not reach GP… (off by X deg)` | Robot stopped (e-stop, protective stop, Manual mode) |
| Twin prints `Waiting for the UI backend...` | Backend not running: `python -m ui.backend.server` in WSL |
| Twin: `RoboDK is not in simulation mode` | Switch RoboDK back to simulation (it must never drive the robot) |
| Station missing items in twin | Run `build_station.py` on that station and save it |
| `rostopic list` shows nothing | `source ./activate_wsl.sh`, check network to 192.168.2.14 |
| Classifier timed out / failed | `bash tests/check_classifier.sh` |
| Crop misses the plate | Rack or GP156 moved → adjust `ROI` in `rack_classifier.py`, retrain |
